# infra — the-invisible-cities.com

Production runs on the shared DigitalOcean droplet described in
`~/Code/util/infra/` (OS, nginx globals, backups, restore). This directory is
everything specific to this site. Facts as of 2026-10-23.

## Where it lives

| | |
|---|---|
| Domain | `the-invisible-cities.com` (`www.` → 301 to the apex; port 80 → 301 to https) |
| Stack | Kirby 5 flat-file CMS on PHP 8.5-FPM (`/run/php/php8.5-fpm.sock`), no database |
| Site root | `/home/forge/the-invisible-cities.com/current/` → `releases/<id>/`, 4 releases kept (Forge setting) |
| Forge site id | `3311015` (appears in `forge-conf/3311015/…` and the error-log name) |
| TLS | Let's Encrypt via Forge, renewed Mon 11:01 (`/root/.letsencrypt-renew/3647249`) |
| Runs as | `forge` |

No daemons or queue workers. One scheduled job, defined in Forge's Scheduler (documented in `crontab`): a weekly
`rm -rf /mnt/data-volume/media/pages/* <current>/site/cache/the-invisible-cities.com/pages` that empties Kirby's generated page-media cache **and** the static page cache. Both must go together: cached HTML references thumbnails that only exist (or can be regenerated, via `.jobs/*.json`) until the media wipe, so wiping media alone makes cached pages 404 their images.

Everything Kirby writes (orders, journal, uploaded media, accounts) lands
on the volume through those symlinks, so the volume snapshot is the backup of record.
The real secrets (Stripe, Mailgun, Kirby `.license`) are in
`/mnt/data-volume/site/config/config.php` and `.license`, not in `.env`. One release
still carries a stray `config.the-invisible-cities.ca.php -> config.php` symlink from
before the domain change; `forge_deploy.sh` no longer creates it.

## Deploy

1. Push to `master` → `.github/workflows/deploy.yml` (environment `production`) calls the
   Forge deploy-trigger URL (secret `FORGE_DEPLOY_URL`) with the commit, author and message.
2. Forge runs `forge_deploy.sh`: `$CREATE_RELEASE()` (clone into `releases/<id>`, submodules),
   strips the token from the remote URL, builds the symlinks above, `pnpm install` +
   `pnpm run prod`, then `$ACTIVATE_RELEASE()` (swap `current`, prune old releases) and
   `sudo service php8.5-fpm reload` — required, because OPcache runs with
   `validate_timestamps=0`.
3. The workflow polls the Forge API until that deployment is `finished`/`failed`, then curls
   the site.

`forge` is allowed `service php8.5-fpm reload` without a password (`util/infra/droplet.md`).

## Page cache (Staticache)

Kirby's `getkirby/staticache` plugin writes every rendered page to
`site/cache/<host>/pages/<path>/index.html` (inside the release, so each deploy starts with an
empty cache), and the vhost's `location /` serves those files straight from disk before falling
back to `index.php` (`nginx.conf`, "Site links"). A cache hit never starts PHP; a miss renders
through Kirby and writes the file for next time. Panel edits purge the cache automatically.

How the pieces fit — change one and the others must follow:

| Where | What |
|---|---|
| `nginx.conf` → `location /` | `try_files` looks in `/site/cache/$host/pages/…`; any verb other than GET/HEAD skips the cache and goes to PHP. Applied **by hand** on the server (below). |
| `site/config/config.the-invisible-cities.com.php` (on the volume, `/mnt/data-volume/site/config/`) | The `cache.pages` block. Not in git; the template is `site/config/config.base`. |
| `.ddev/nginx_full/nginx-site.conf` | The same `location /` for local testing |

Production `cache.pages` must read:

```php
'cache' => [
    'pages' => [
        'active'  => true,
        'type'    => 'static',
        'headers' => false,   // nginx can't read the header block `true` stores; the files must be body-only
        'ignore'  => function ($page) {   // exact page ids only: array entries are NOT wildcards
            $id = $page->id();
            return $id === 'home' || $id === 'prints' || str_starts_with($id, 'prints/');
        },
    ],
],
```

Things that behave differently once nginx serves the files:

- A served page skips **all** PHP: no session, cart, geolocation or CSRF logic runs for it. That is why
  `home` and everything under `prints` are ignored, and why Kirby itself refuses to cache a page that
  touches the session.
- Changing `ignore` does not remove files already cached; delete them
  (`rm -rf site/cache/<host>/pages/prints*`) or they keep being served.
- `headers => true` and this nginx rule are incompatible (the status/header lines would be sent as page body).
- After a deploy the first visit to each page is slow (it is the one that writes the file).

**Rolling it out on the server** (steps 1 and 3 as `forge`, step 2 as root because it writes `/etc/nginx`):

1. Edit `/mnt/data-volume/site/config/config.the-invisible-cities.com.php`: set `headers` to `false` and
   replace the `ignore` array with the closure above (`php -l` it).
2. Copy `nginx.conf` to `/etc/nginx/sites-available/the-invisible-cities.com`, then `nginx -t && service nginx reload`.
3. Clear the stale cache so the new ignore rule takes effect: `rm -rf /home/forge/the-invisible-cities.com/current/site/cache/the-invisible-cities.com/pages`.
4. `./snapshot.sh` — the vhost should report no drift.

Check it on a real request with `curl -sI <url>`: a hit is a plain file from nginx, so it carries `ETag` and
`Last-Modified`; a page rendered by Kirby has neither. (Don't look for `X-Powered-By`: `expose_php` is Off.)
Request a not-yet-cached URL twice: no `ETag` the first time, an `ETag` the second.

## Leaving Forge — what needs a new owner

- **Release handling** — clone, symlinks, `current` swap, pruning old releases, the `.env` link
  into each release (Forge does that last one; the script doesn't).
- **Deploy trigger and status** — replace the curl + Forge API polling in `deploy.yml` with SSH
  as `forge` running the deploy script, and use its exit status.
- **vhost includes** — inline `forge-conf/3311015/site.conf` and the two redirect files into
  `nginx.conf`, drop the `# FORGE …` include lines.
- **TLS** — the `ssl_certificate` paths point at Forge-managed directories that change on every
  renewal (`/etc/nginx/ssl/domains/1860889/<cert-id>/`). A replacement (certbot webroot or
  acme.sh) needs to keep `/.well-known/acme-challenge/` served from `/home/forge/.letsencrypt/`
  (the vhost already does).
- **Logrotate** entry `forge-3311015`.
- **The scheduled job** in `crontab`.
